# FoodShare Vyatsu

FoodShare — MVP-платформы, которая помогает кафе, ресторанам и пекарням продавать непроданные продукты по сниженной цене, а покупателям находить такие предложения. Репозиторий содержит клиентское приложение, API и конфигурацию локальной инфраструктуры.

Это руководство описывает настройку среды разработки, запуск локально и через Docker, работу с базой данных и типовой Git-процесс. Проект находится в разработке: ниже отдельно отмечены возможности, которые пока не реализованы в коде.

## Технологии и состав проекта

- **Клиент:** React 18, TypeScript, Vite, Tailwind CSS, Lucide React.
- **Сервер:** Node.js 20, Express, TypeScript.
- **База данных:** PostgreSQL 16, доступ через Prisma ORM.
- **Redis:** Redis 7; сервис включён в Compose, но сейчас серверное приложение его не использует.
- **Веб-сервер в контейнере клиента:** Nginx; раздаёт собранный SPA и проксирует `/api/` к серверу.
- **CI:** GitHub Actions собирает клиент и сервер на Node.js 20 для push и pull request в `main` и `develop`.

## Требования

Для локальной разработки понадобятся:

1. Git.
2. Node.js 20.x и npm.
3. Docker Desktop с Compose plugin — удобно использовать для PostgreSQL и Redis.
4. Доступный локально порт `5173` для Vite, `5000` для API, `5432` для PostgreSQL и `6379` для Redis.

Для запуска всего проекта в контейнерах дополнительно нужен свободный порт `80`.

Проверить установленные версии:

```bash
git --version
node --version
npm --version
docker --version
docker compose version
```

## Получение проекта

Подставьте URL репозитория, доступный вашей команде:

```bash
git clone <URL-репозитория>
cd foodshare_vyatsu
git switch develop
git pull --ff-only origin develop
```

Если в проекте принято начинать работу с другой ветки, используйте её вместо `develop`. Основные ветки `main` и `develop` указаны в CI workflow.

## Локальный запуск

В этом варианте Vite и API запускаются на хост-машине, а PostgreSQL и Redis — в Docker. Запускайте команды в отдельных терминалах из корня репозитория.

### 1. Запустить PostgreSQL и Redis

```bash
docker compose up -d postgres redis
docker compose ps
```

Compose создаёт PostgreSQL с базой `foodshare_db`, пользователем `foodshare_user` и паролем `secretpassword`. Эти значения предназначены только для локальной разработки.

### 2. Настроить сервер

Создайте локальный файл окружения из шаблона:

```bash
cp .env.example server/.env
```

Файл `server/.env` исключён из Git. Убедитесь, что `DATABASE_URL` указывает на локальный PostgreSQL на `localhost:5432`, как в шаблоне. Не используйте демонстрационные секреты и пароли в общедоступной или production-среде.

Установите зависимости, сгенерируйте Prisma Client и синхронизируйте схему с локальной базой:

```bash
cd server
npm install
npx prisma generate
npx prisma db push
npm run dev
```

`npm run dev` запускает сервер через `tsx watch`; после изменения серверного TypeScript-кода процесс перезапускается автоматически. API доступно на `http://localhost:5000`.

Чтобы загрузить тестовую пекарню и бокс, откройте второй терминал:

```bash
cd server
npx prisma db seed
```

Скрипт seed при каждом запуске создаёт новую запись пекарни с вложенным боксом. Это не идемпотентный скрипт: повторный запуск добавит ещё одну запись.

### 3. Запустить клиент

В новом терминале:

```bash
cd client
npm install
npm run dev
```

Откройте адрес Vite, обычно `http://localhost:5173`. Vite проксирует запросы `/api` на `http://localhost:5000`, поэтому для разработки используйте относительный путь `/api/...`.

### 4. Проверить API

Откройте `http://localhost:5000/api/health`. Ожидаемый ответ:

```json
{
  "status": "ok",
  "message": "FoodShare API is operational"
}
```

## Запуск через Docker Compose

Compose описывает четыре сервиса: PostgreSQL, Redis, сервер и клиент. Для сборки и запуска:

```bash
docker compose up --build
```

В фоновом режиме:

```bash
docker compose up --build -d
```

После успешного старта клиент должен быть доступен на `http://localhost`, API — на `http://localhost:5000/api/health`.

Полезные команды Compose:

```bash
docker compose ps
docker compose logs -f
docker compose logs -f server
docker compose logs -f client
docker compose restart server
docker compose down
```

`docker compose down` останавливает и удаляет контейнеры, но сохраняет volume базы. Чтобы **полностью удалить локальные данные PostgreSQL**, включая volume, выполните `docker compose down -v`. Эта команда необратимо удаляет данные базы.

### Важное замечание о сборке образов

Dockerfile сервера и клиента, а также CI используют `npm ci`, для которого необходим соответствующий `package-lock.json`. В текущем дереве репозитория lock-файлы отсутствуют. Поэтому Docker-сборка и CI могут завершиться ошибкой до установки зависимостей.

Чтобы подготовить lock-файлы, выполните `npm install` отдельно в `server/` и `client/`, проверьте появившиеся `package-lock.json` и добавьте их в Git. После этого локальные чистые установки и контейнерные сборки следует выполнять через `npm ci`. Не заменяйте `npm ci` на `npm install` в CI как обход: lock-файл делает установку воспроизводимой.

Текущий Compose не выполняет Prisma-миграции при старте сервера. Изменение схемы для контейнерного запуска нужно сначала применить к базе отдельной командой (см. раздел [Работа с базой данных](#работа-с-базой-данных)); при необходимости `prisma generate` выполняется во время сборки образа сервера.

## Переменные окружения

Шаблон настроек находится в `.env.example`:

| Переменная | Назначение | Локальное значение из шаблона |
| --- | --- | --- |
| `PORT` | Порт Express API | `5000` |
| `NODE_ENV` | Режим запуска Node.js | `development` |
| `DATABASE_URL` | Строка подключения Prisma к PostgreSQL | `postgresql://foodshare_user:secretpassword@localhost:5432/foodshare_db?schema=public` |
| `REDIS_URL` | Адрес Redis | `redis://localhost:6379` |
| `JWT_SECRET` | Секрет подписи JWT | демонстрационный; замените для любой общей среды |
| `JWT_EXPIRES_IN` | Срок действия JWT | `7d` |

Для локального запуска API положите настроенный файл в `server/.env`. Не коммитьте `.env`, токены, пароли и настоящие секреты. Compose сейчас задаёт собственные значения переменных непосредственно в `docker-compose.yml`; он не подхватывает автоматически все значения из `server/.env`.

## Работа с базой данных

Описание моделей находится в `server/prisma/schema.prisma`. Сейчас схема содержит `User`, `Restaurant`, `Box` и `Order`.

Перейдите в каталог сервера перед выполнением команд Prisma:

```bash
cd server
```

Сгенерировать Prisma Client после установки зависимостей или изменения схемы:

```bash
npx prisma generate
```

Синхронизировать схему с локальной базой без создания файлов миграций:

```bash
npx prisma db push
```

Создать и применить миграцию для изменения схемы при локальной разработке:

```bash
npm run prisma:migrate -- --name describe_change
```

Например: `npm run prisma:migrate -- --name add_box_description`. Проверяйте и добавляйте созданные файлы миграций в Git вместе с изменением `schema.prisma`. Не редактируйте уже применённые общие миграции так, будто они ещё не публиковались.

Заполнить базу seed-данными:

```bash
npx prisma db seed
```

Для просмотра/редактирования данных можно запустить Prisma Studio:

```bash
npx prisma studio
```

`db push` удобен для первого локального старта, но не заменяет версионируемые миграции в командной разработке. Для общей базы или развёртывания используйте проверенные миграции и согласованный процесс релиза.

## Полезные команды

Команды запускаются из соответствующего каталога.

| Каталог | Команда | Назначение |
| --- | --- | --- |
| `client/` | `npm run dev` | Запустить Vite dev server на порту `5173` |
| `client/` | `npm run build` | Проверить TypeScript и собрать клиент в `dist/` |
| `client/` | `npm run preview` | Локально посмотреть production-сборку клиента |
| `server/` | `npm run dev` | Запустить API с перезапуском при изменениях |
| `server/` | `npm run build` | Проверить TypeScript и собрать сервер в `dist/` |
| `server/` | `npm start` | Запустить собранный сервер из `dist/` |
| `server/` | `npm run prisma:generate` | Сгенерировать Prisma Client |
| `server/` | `npm run prisma:migrate -- --name <name>` | Создать и применить миграцию Prisma |

Отдельных npm-скриптов для тестов и линтинга в текущих `package.json` нет. CI сейчас выполняет установку зависимостей, генерацию Prisma Client и сборки обеих частей.

## Работа с Git

Рекомендуемый поток для небольшой задачи:

1. Перейдите на актуальную базовую ветку и обновите её:

	```bash
	git switch develop
	git pull --ff-only origin develop
	```

2. Создайте отдельную ветку:

	```bash
	git switch -c feature/short-description
	```

	Для исправлений можно использовать имя вида `fix/short-description`. Следуйте принятому в команде формату имён, если он отличается.

3. Проверьте изменения и соберите нужные части проекта:

	```bash
	git status
	git diff
	```

	Для клиентского изменения запустите `npm run build` в `client/`; для серверного — `npm run build` в `server/`. Если менялась схема БД, также проверьте миграцию и Prisma Client.

4. Добавьте только относящиеся к задаче файлы, создайте коммит и отправьте ветку:

	```bash
	git add <файлы>
	git diff --cached
	git commit -m "feat: краткое описание изменения"
	git push -u origin feature/short-description
	```

5. Откройте pull request в `develop` (или в целевую ветку, согласованную командой) и проверьте результат CI.

Полезные Git-команды:

```bash
git status --short --branch
git branch --all
git log --oneline --decorate -10
git diff
git diff --staged
git fetch origin
```

Перед коммитом убедитесь, что локальные `.env` и другие секреты не попали в staged changes: `git status` и `git diff --cached` показывают, что именно будет отправлено. Не используйте `git add .`, если в рабочем дереве есть посторонние файлы.

## Текущее состояние и ограничения

- В API сейчас зарегистрирован health-check `/api/health`; наличие каталогов контроллеров, маршрутов и сервисов само по себе не означает, что бизнес-эндпоинты уже подключены.
- JWT и bcrypt указаны в первоначальном описании концепции, но текущая серверная точка входа пока не реализует полноценную аутентификацию.
- Redis описан в Compose и шаблоне переменных окружения, но серверный код пока не подключает Redis-клиент.
- В проекте есть схема Prisma и seed, но каталог с применяемыми миграциями в репозитории пока не представлен.
- Текущий seed не проверяет наличие уже созданной тестовой записи и при повторном запуске добавляет новую.
- `npm ci` в Docker и CI требует lock-файлы; создайте и закоммитьте их отдельно для `client/` и `server/`, прежде чем рассчитывать на чистую CI-сборку.
- Compose содержит демонстрационные пароли и JWT secret. Это локальная конфигурация, не подходящая для публикации сервиса.

## Решение проблем

### Порт уже занят

Если Vite сообщает, что занят `5173`, API не может открыть `5000`, или PostgreSQL/Redis не стартуют, остановите процесс, занимающий порт, либо измените локальную конфигурацию порта. Для клиентского Vite-порта смотрите `client/vite.config.ts`; API-порт задаётся `PORT`. Для Docker-портов меняется левая часть записи `host:container` в `docker-compose.yml`.

### API не подключается к базе

- Убедитесь, что контейнер запущен: `docker compose ps`.
- Проверьте, что `DATABASE_URL` в `server/.env` использует `localhost`, если API запущен на хосте.
- Если API запущен контейнером, адрес базы в Compose должен быть именем сервиса `postgres`, а не `localhost`.
- Посмотрите логи PostgreSQL: `docker compose logs -f postgres`.
- После изменения `schema.prisma` выполните `npx prisma generate` и примените схему/миграцию.

### Запросы из клиента не доходят до API

- При разработке Vite проксирует `/api` на `http://localhost:5000`; проверьте, что сервер запущен и health-check отвечает.
- В Docker Nginx проксирует `/api/` к сервису `server` внутри Compose-сети.
- Не вызывайте `localhost` из браузерного кода как адрес backend при Docker-развёртывании; используйте настроенный публичный адрес или относительный `/api`.

### `npm ci` завершается ошибкой

Убедитесь, что в соответствующем каталоге есть закоммиченный `package-lock.json`, соответствующий `package.json`. Если lock-файла ещё нет, выполните `npm install` в каталоге `client/` и отдельно в `server/`, затем добавьте оба lock-файла в Git.

### Контейнеры запускаются, но приложение не готово

`depends_on` задаёт порядок запуска контейнеров, но сам по себе не гарантирует, что PostgreSQL уже принимает соединения. Проверьте логи сервисов и повторите подключение после готовности базы. Также учтите, что Compose не запускает миграции автоматически.
